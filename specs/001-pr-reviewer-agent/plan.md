## Summary

## Summary

Build a continuously-running GitHub PR Review Agent that lives in Docker, is triggered by GitHub webhooks (per-repo, registered for the configured PAT account) whenever a PR is opened/updated or CI/CD completes, and automatically executes reviews by spawning a one-off `opencode run` CLI subprocess. It gates reviews on CI (green heads only; a failing gate posts a root-cause diagnosis comment), performs security analysis (gitleaks secrets scan + LLM security review in-session), validates PR scope (ensuring changed files match PR details/issues) and test compliance (discovery only — the container never runs the repo's test suites). Self-contained minimal skills (`agent_skill_set`, vendored in `.agents/skills/`) and this repo's `specs/<owner>/<repo>/` docs are passed as context, reviews are deduplicated per (repo, PR, head SHA, model), model selection is per-PR via `@review --model <alias>`, transient failures retry with backoff, and a periodic reconcile sweep plus an idempotency marker guard against missed events and duplicate posts.

## Technical Context

**Language/Version**: Python 3.11+ / FastAPI (single `src/` package layout)

**Primary Dependencies**: GitHub REST API client (`httpx`), FastAPI (ASGI) + uvicorn for the webhook endpoint, `aiosqlite` (SQLite with WAL), `pydantic` + `pyyaml` config parsing, opencode CLI (`opencode run` subprocess), gitleaks

**Storage**: SQLite state database (`review_runs`, `repos`, `model_aliases`, `repo_config`) plus isolated on-disk clone workspace (`/var/agent_cache/repos`) seeded by plain HTTPS clone and `.runs/` JSON run records

**Testing**: The feature's own unit/integration/system tests (pytest + pytest-asyncio) testing webhook parsing, the opencode CLI subprocess runner, CI-gate handling, and scope/compliance validation

**Target Platform**: Linux container (Docker compose: app + `ngrok/ngrok` sidecar), reachable via the ngrok tunnel with `opencode run` invoked per review

**Project Type**: web-service / background daemon

**Performance Goals**: webhook ACK within 2 seconds; review posted within 15 minutes of gating CI completing for the head (or within 15 minutes of the no-CI settle window); serial execution (concurrency default 1)

**Constraints**: Docker compose deployment (app + `ngrok/ngrok` sidecar); image includes a Python 3.11+ runtime with FastAPI, the opencode CLI, git, and gitleaks; GitHub PAT (`repo` scope) used for all REST calls and webhook registration; secrets supplied only via a gitignored `.env` (`env_file`); never push/commit to reviewed repos; disk cap with LRU clone eviction

**Scale/Scope**: single-user personal service; reviews only repos listed in `repo_config`, minus `denylist`; per-repo docs in this repo's `specs/` tree

## Complexity Tracking

No complexity deviations from Constitution simplicity rules. The separation between webhook handling and the review worker pipeline is required by REQ-NF-002 (sub-2s ACK with asynchronous processing) and REQ-NF-006 (bounded concurrency), not incidental.

> | Violation | Why Needed | Simpler Alternative Rejected Because |
> |-----------|------------|-------------------------------------|
> | Webhook/pipeline separation (ARCH-001/002 vs ARCH-003) | Webhook ACK must stay under 2s while reviews take minutes (REQ-NF-002) | Single synchronous handler would block GitHub delivery and violate REQ-NF-002 |
> | SQLite + queue with crash-safe semantics | At-least-once, idempotent processing with no orphaned locks and no double-post (REQ-NF-005) | In-memory queue loses state on restart and cannot satisfy restart-safe recovery |
